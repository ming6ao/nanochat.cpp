# The performance model

Status: implemented for phases M0 to M4. The counter table, the precision
assignment, the device limit table, the estimator, and the report numbers are in
the tree, and `tools/nanochat roofline` prints the roofline report. The
attainment record of section 10 is generated by `tools/nanochat attain`, which
joins a bound with a measurement; the in-tree depth-24 measurement is still
pending, so the record holds one reference row.

The tree has a throughput calculation for the MFU line, and a
standalone estimator in `.agents/skills/model-fit/scripts/model_fit.py`. This
document turns the second one into a project artifact, and binds it to the
device limit table and to the benchmark report.

The model answers one question without a GPU: what is the fastest possible step
at this shape, and what limits it?

- [performance.md](performance.md) — the measurement protocol.
- [simulator.md](simulator.md) — the S0 simulator and its limits.
- [kernels.md](kernels.md) — the kernel inventory the model counts.
- [fp8-training.md](fp8-training.md) — the fp8 tier and the layer set.

## 1. Goal and scope

**Goal.** Report the bound on the step time from the device limits, the
operation that binds, and the distance from the measured step to the bound.

**In scope.**

- One structural counter table that lists the arithmetic, the bytes, and the
  launch count of each operation.
- One precision assignment, so each operation uses its own peak rate.
- One device limit table: the peak rate per precision, and the peak bandwidth.
- One roofline estimator that uses the peak limits directly.
- A work-ratio check that reports redundant issued work.
- A report that carries the numbers a run reports, so a bound and a measurement
  join.
- An attainment record that compares the bound with the measured step.

**Out of scope.**

- A fitted correction factor. The model uses the device peaks, and nothing else.
- A cycle-accurate model.
- A full memory-system simulation.
- A model of the data loader and of the checkpoint write.

## 2. Why the simulator is not enough

The S0 simulator proves values. It does not prove time.

| Engine | Proves | Gives time |
|---|---|---|
| Reference engine | The graph arithmetic | No |
| API interposer | The call shape | No |
| Emulation engine | The device-code arithmetic | No |
| Performance model | The step-time bound | Yes |

The reference engine runs on the CPU at the CPU rate. The emulation engine runs
each CUDA thread as a host fiber, at the host rate. Neither rate is the device
rate.

`docs/simulator.md` section 14 marks a functional PTX interpreter as a non-goal.
A cycle-accurate model is a large project with a small return. The device peaks
give a useful bound at a small cost.

## 3. The inputs

The model has three inputs. Each one has one owner and one stored form.

| Input | Source | Stored in |
|---|---|---|
| The operation counters | The model configuration | A counter struct in `src/performance_model.cc` |
| The precision assignment | The fp8 rule and the layer set | `docs/fp8-training.md` |
| The device limits | The device profile table | `include/nanochat/device_profile.h` |
| The launch cost | A device property | The device profile table |

The model holds no fitted value. A number that comes from a measurement appears
in the attainment record only, and never in the estimator.

## 4. The operation counter table

The tree counts the total arithmetic today. `EstimateFlopsPerToken` in
`src/performance_model.cc` returns one number. The model needs the parts, each
with its precision.

Add one struct beside `NumMatmulParams` and `CountParams`:

```cpp
struct FlopCounts {
  double gemm_forward;      // 2 * params * tokens
  double gemm_backward;     // 4 * params * tokens
  double attention_forward;
  double attention_backward;
  double norm_and_pointwise;
  double classifier;
  double embedding;
};
```

Fill it from the same terms that `EstimateFlopsPerToken` uses. Keep
`EstimateFlopsPerToken` as the sum of the fields, so one source of truth
remains. `include/nanochat/mfu.h` owns the declaration.

Each row of the counter table also carries three non-arithmetic fields:

- the precision, for the rate selection;
- the operand bytes, for the memory-bound case;
- the launch count, for the launch overhead.

| Operation | Arithmetic | Precision | Operand bytes | Launch count |
|---|---|---|---|---|
| `c_q`, `c_k`, `c_v`, `c_proj` | `2 * p * t` forward, `4 * p * t` backward | The assigned GEMM precision | The activations and the weights | One per call |
| `mlp.c_fc`, `mlp.c_proj` | Same form | The assigned GEMM precision | Same | One per call |
| the language-model head | Same form | The assigned GEMM precision | Same | One per call |
| the quantization cast | A row pass | Not applicable | 5 bytes per element | One per operand |
| the layout copies | A copy | Not applicable | The operand size | One per copy |
| the attention scores | `4 * h * d * w` forward over the window `w` | The attention precision | The score matrix | One per tile group |
| the attention output | `4 * h * d * w` forward | The attention precision | The probability matrix | One per tile group |
| the attention backward | `8 * h * d * w` | The attention precision | The score and probability matrices | One per tile group |
| the norms and the pointwise steps | A row pass | The compute precision | The row buffers | One per call |
| the classifier | A row pass over the vocabulary | fp32 | The logits | One per call |
| the embedding | A gather and a scatter | The compute precision | The table rows | One per call |
| the optimizer | A stateful pass | fp32 | Three buffers | One per tensor |
| the Muon orthogonalisation | Three GEMMs per Newton-Schulz iteration | The compute type | The gradient and the update | One per matrix |

Here `p` is the matrix parameter count, `t` the token count, `h` the head
count, `d` the head width, and `w` the effective window.

## 5. The precision assignment

A single build precision is not enough. The reference nanochat converts only
some of the matrix multiplies, and it keeps the rest in bf16 or fp32. The model
must select a rate per operation.

### 5.1 The rule from the reference

The reference applies `--fp8` through a module filter. A Linear layer converts
when all three conditions hold:

1. it is a matrix multiply;
2. both dimensions are divisible by 16;
3. the smaller dimension is at least 128.

The reference then uses two fp8 formats. The forward operands use E4M3. The
gradient operand uses E5M2, which has a wider range. The accumulator and the
output stay in the compute type.

Each converted matrix multiply becomes three fp8 GEMMs:

| GEMM | Operand A | Operand B | Accumulator | Output |
|---|---|---|---|---|
| Forward | The activation, E4M3 | The weight, E4M3 | fp32 | bf16 |
| Input gradient | The output gradient, E5M2 | The weight, E4M3 | fp32 | bf16 |
| Weight gradient | The output gradient, E5M2 | The activation, E4M3 | fp32 | bf16 |

The reference computes the forward with a fast accumulation mode. The two
backward GEMMs use the full fp32 accumulation.

### 5.2 The assignment at depth 24

| Operation | Precision | Reason |
|---|---|---|
| `c_q`, `c_k`, `c_v`, `c_proj` | fp8 | A matrix, and both dimensions are 1536 |
| `mlp.c_fc` | fp8 | A matrix, 1536 by 6144 |
| `mlp.c_proj` | fp8 | A matrix, 6144 by 1536 |
| `lm_head` | fp8 | A matrix, 1536 by 32768 |
| `ve_gate` | bf16 | The output width is 12, which is below 128 |
| `smear_gate` | bf16 | The output width is 24, which is below 128 |
| the embeddings | bf16 | A gather, not a matrix multiply |
| the attention | bf16 | The flash attention engine runs bf16 |
| the norms and RoPE | bf16 | A row kernel |
| the softmax and the saved statistics | fp32 | A row reduction with an exponential |
| the classifier softcap | bf16 | A row kernel |
| the loss | fp32 | The loss must stay fp32 |
| the optimizer | fp32 | The state must stay fp32 |
| the gradient reduction | The gradient type | The native plan reduces in fp32 |

At depth 24 the eligible matrices hold 729.8 million parameters. The two gates
hold 1,752 parameters. So the assignment is simple: the matrix multiplies run
in fp8, and everything else runs in bf16 or fp32.

### 5.3 The two costs that come with fp8

fp8 is not free. Two terms appear that do not exist in a bf16 run.

**The quantization cast.** Each operand must be measured, scaled, and cast
before the GEMM. The amax pass reads the operand, and the cast pass reads it
again and writes one byte per element. A fused kernel needs about five bytes of
traffic per element. An unfused sequence of framework calls needs more.

**The layout copies.** The fp8 GEMM engine requires the first operand
row-major and the second operand column-major. A tensor that is already in the
wrong layout needs a physical copy.

The reference performs three copies per backward call. This project can avoid
most of them: store the weight in the layout the GEMM wants, once, and use that
layout for every step. This is a design requirement, not a tuning detail.

## 6. The device limit table

The limit table is a declaration, not a header. Each device entry in
`backends/<name>/caps.json` states the rates and the cost, and
`src/device_profile.cc` derives one profile row from it. A device bring-up adds
one entry and no row anywhere else.

| Field | Meaning |
|---|---|
| `peak_fp32_flops` | The CUDA-core rate, dense |
| `peak_bf16_flops` | The tensor-core rate, or 0 when the card has no bf16 |
| `peak_fp8_flops` | The E4M3/E5M2 tensor-core rate, or 0 |
| `peak_bandwidth_bytes_per_second` | The peak HBM rate |
| `launch_us` | The nominal cost of one launch |
| `reference_peak_flops` | The rate the *reference* recipe's MFU line divides by |
| `reference_precision` | The precision `reference_peak_flops` is quoted at |

The rates are dense and non-sparse. State that in a declaration, because a
vendor sheet often quotes the sparse rate.

The ridge point is a rate divided by the bandwidth. It decides which limit
binds, and section 7 uses it.

### 6.1 One number per card

One accessor answers every consumer. `PeakFlopsFor(profile, precision)` in
`nanochat/device_profile.h` is a single switch over the declared rates, and the
benchmark's share, the training log's MFU line, and the estimator all reach a
card's rate through it.

The tree has two *purposes*, not two tables:

| Function | Rate it reads | Use |
|---|---|---|
| `PeakFlopsForDevice` | `reference_peak_flops` | The reference MFU line |
| `PeakFlopsForCompute` | `PeakFlopsFor(profile, precision)` | The project MFU line, per operation |

Both read the one declaration. A card whose reference recipe counts at bf16
tensor cores reports that rate from the first function and its per-precision
rates from the second, so the two differ by design and cannot disagree about a
number, because the number appears once.

`//tests:device_profile_test` enforces three rules. The first is that
`reference_peak_flops` equals one of the declared rates. The second is that
`reference_precision` is the precision the documented rule selects: bf16 when
the card has bf16, fp32 otherwise. The third is that `PeakFlopsForDevice` reads
exactly that field.

A card with no declaration has no rate: `PeakFlopsForDevice` answers 0 and a
benchmark reports no share. That is the honest answer, and it is the one the
`bench.h` caption prints.

### 6.2 One answer for an unknown device

A name no declaration owns is refused, not priced at zero. `DeviceNameError` in
`nanochat/device_profile.h` renders the message, and `DeviceNameList` gives the
declared set. The roofline report and the simulator then refuse the same name
with the same text and the same exit status, so a mistyped device is a command
error and never a report of zeros that reads like a very fast step.

`tools/nanochat devices` prints the declared set. The simulator validates
against it, so adding a device is one `devices[]` entry and the command line
needs no edit.

### 6.3 A vendor spelling resolves to one row

`FindDeviceProfile` lowercases and strips the whitespace of a name, then looks
for an exact match and then for a declared name inside it. The **longest**
declared name wins, so the rule does not depend on the order the table happens
to be sorted in. `NVIDIA H100 80GB HBM3` resolves to `h100`, and a run that
reports its own marketing name still reaches a declaration.

A sub-SKU with its own rate needs its own entry. The tree declares no `h100nvl`
row, so an H100 NVL resolves to `h100` and both the reference line and the
estimator divide by the `h100` rate. A card whose rated peak differs from the
declared one is a missing declaration, and the fix is an entry, never a second
table.

## 7. The estimator

The estimator is the roofline. Each operation has two limits, and the bound is
the larger of the two.

```text
compute_time = flops / peak_rate[precision]
memory_time  = bytes / peak_bandwidth
time         = max(compute_time, memory_time) + launch_time
bound        = sum(time) + sync_time
```

| Term | Formula | Source |
|---|---|---|
| `compute_time` | `flops / peak_rate[precision]` | The counter table and the limit table |
| `memory_time` | `bytes / peak_bandwidth` | The counter table and the limit table |
| `launch_time` | `launches * per_launch_us` | The device limit table |
| `sync_time` | `2 * (n - 1) / n * payload / link_bandwidth` | The topology |

The bound is an upper limit. A measured step below the bound is normal. The gap
is the finding, and section 9 shows how to read it.

### 7.1 The roofline

The roofline decides which limit binds. The arithmetic intensity is the
arithmetic divided by the bytes.

At the depth-24 shape on the H100, in bf16:

| Operation | Intensity (FLOP/byte) | Limit |
|---|---:|---|
| `c_q`, `c_k`, `c_v` (`32768 x 1536 x 1536`) | 750 | Compute |
| `mlp.c_fc` (`32768 x 6144 x 1536`) | 1,184 | Compute |
| `mlp.c_proj` (`32768 x 1536 x 6144`) | 1,184 | Compute |
| the language-model head (`32768 x 32768 x 1536`) | 1,404 | Compute |
| the attention scores (`2048 x 2048 x 128`) | 114 | Memory |
| the attention output (`2048 x 128 x 2048`) | 114 | Memory |
| the quantization cast | Near 0 | Memory |
| the layout copies | 0 | Memory |

The bf16 ridge point on the H100 is 295 FLOP/byte. `1979e12 / 3.35e12` gives
591 FLOP/byte in fp8. The matrix multiplies stay above both ridge points even
after the rate doubles, so they remain compute bound.

Two families sit far below the ridge point: the dense attention, and the
quantization cast. Both are memory bound, and both use the bf16 or fp8 rate
only in name. This is the most useful result of the model.

### 7.2 The bound at the depth-24 shape

Take 24 layers, 12 heads, head width 128, sequence 2048, `SSSL`, and 5.84
billion tokens on eight H100 cards.

| Term | bf16 everywhere | The reference fp8 | The C++ fp8 target |
|---|---:|---:|---:|
| The matrix multiplies | 54 min | 28 min | 28 min |
| The quantization cast, fused | — | 13 min | 13 min |
| The fp8 layout copies | — | 1 min | About 0 |
| The attention, bf16 | 5 min | 5 min | 5 min |
| The gradient sync | 1.5 min | 1.5 min | 1.5 min |
| **Subtotal** | **61 min** | **48 min** | **47 min** |
| The row kernels: the norms, the pointwise steps, the classifier, the embedding | 6 min | 6 min | 6 min |
| The optimizer state and the Muon orthogonalisation | 3 min | 3 min | 3 min |
| **Step bound** | **70 min** | **57 min** | **56 min** |

Every figure comes from `tools/nanochat roofline` with `--muon-ns-steps 5`, and
the reference column adds `--reference-copies`. The three columns model one
step of 757.1 ms, 612.1 ms, and 606.8 ms.

Three results follow.

1. **fp8 is worth about 14 minutes of the bound at this shape.** The GEMM term
   falls by 27 minutes. The cast gives 13 minutes back. The gain is real, and it
   is not a factor of two.
2. **The cast must be one fused kernel per operand.** At five bytes per element
   the cast costs 13 minutes. At sixteen bytes it costs 42 minutes, and at
   thirty-two bytes it costs 84 minutes. An unfused cast makes fp8 slower than
   bf16.
3. **The layout is a design decision.** The reference pays about half a minute
   for its per-step weight copies, and most of that is 1,740 extra launches, not
   traffic. Store the weight in the required layout once, and the term
   disappears. The row prices the weight only; the reference also copies
   activations, which the counter table does not carry.

The fp32 fused attention tile would change the attention row from 5 minutes to
120 or 240 minutes. See
[attention.md](attention.md).

The nanochat reference measured 99 minutes against a step bound of about 57
minutes. The fraction is about 0.57. The remaining 42 minutes are the launch
gaps, the imperfect overlap, and the achieved GEMM rate. Section 7.4 splits the
bound by phase and by row, which is where that measurement belongs.

### 7.3 The bound at the two chain shapes

The chain of [post-training.md](post-training.md) runs two
shapes, `demo` (2 layers, hidden 64) and `standard` (8 layers, hidden 512), on
two cards, a T4 at fp32 and an H100 at bf16. `tools/nanochat roofline` prints the
bound of each of the four pairs. The command for one row:

```
tools/nanochat roofline --device h100 --precision bf16 \
    --layers 8 --heads 8 --kv-heads 4 --hidden 512 --seq 64 \
    --vocab 487 --padded-vocab 512 --window-pattern L --batch 1 --json
```

| Shape | Card | Precision | Step bound | Binding row |
|---|---|---|---:|---|
| `demo` 2/64 | T4 | fp32 | 0.366 ms | `launch` |
| `demo` 2/64 | H100 | bf16 | 0.173 ms | `launch` |
| `standard` 8/512 | T4 | fp32 | 3.600 ms | `compute` |
| `standard` 8/512 | H100 | bf16 | 0.764 ms | `launch` |

Three results follow.

1. **The chain is bound by launches and by the host program, not by
   arithmetic.** A step at either shape moved 64 tokens: one row of sequence 64,
   because the recorded job's `batch` field is 1. The host program around those
   tokens costs tens of milliseconds. The recorded T4 run of the chain is about
   42 ms per step at the `demo` shape (`docs/campaigns.md`). The
   largest device bound in the table is 3.6 ms, so most of the step time is not
   device time at all.
   Every family of the two `demo` rows reads `limit: launch` except the optimizer
   row of the T4 one, which reads `memory`; the H100 `standard` row answers the
   same way, launches everywhere but its optimizer row.
2. **The one compute-bound row is the T4 at fp32, at the standard shape.** The
   two fp32 GEMM rows carry 0.69 ms and 1.39 ms of the 3.6 ms, because a Turing
   card at fp32 has no rate to spare for 512 hidden units; the rest of the step
   is memory-bound work, the optimizer row and the norm-and-pointwise row. It
   still leaves the step an order of magnitude below the host program, which is
   why the chain records a step time and gates the two legs against each other
   instead of claiming a throughput (gates G2 and G3 of
   [post-training.md](post-training.md) Part 3, section 8).
3. **The bf16 precision does not move the step time.** The H100 `standard` bound
   of 0.764 ms sits inside a step of tens of milliseconds, so a bf16 leg and an
   fp32 leg of the same job cost the same host time. That is why the second leg
   buys a second precision and a second architecture for the proof and not for a
   speedup.

The optimizer row of the `standard` reports reads `limit: memory`: 386 MB of
optimizer state, 1.21 ms on a T4 at fp32 and 0.118 ms on an H100 at bf16, which
is 318 GB/s and 3.26 TB/s against the 320 GB/s and 3.35 TB/s peaks of section 6.
It is the memory-bound family section 7.1 predicts, and its 1.21 ms is the
second largest term of the T4 step, after the backward GEMM. Both figures are
for one device, because the optimizer row is replicated (section 7.4).

### 7.4 The numbers a benchmark reports

The estimator reports the numbers a run reports, so the two join without a
conversion step. The step fields join the training log:

| The report field | The bound | The measurement it joins |
|---|---|---|
| `tokens_per_second` | The tokens of one step over `step_seconds` | The logger's `tok/s` |
| `forward_seconds`, `backward_seconds`, `optimizer_seconds`, `sync_seconds` | The row bounds summed by phase | `fwd_ms`, `bwd_ms`, `opt_ms`, `sync_ms` |
| `model_mfu` | The model arithmetic over the weighted peak | The logger's `mfu` |
| `optim_mfu` | The Muon arithmetic over the compute-type peak | The logger's `optim_tflops` over the same peak |

A *row* joins a benchmark row on four identity keys, and both schemas state
them with the same spelling:

| Key | The bound | The measurement |
|---|---|---|
| `family` | The operation, with no phase and no shape in it (`attention`, `gemm`) | The same operation |
| `phase` | `forward`, `backward`, `optimizer`, or `sync` | The same phase, or empty |
| `precision` | The rate the row is charged at: `fp32`, `bf16`, or `fp8` | The precision the arithmetic ran at |
| `shape` | The workload, as `key=value` tokens | The same workload |

Both sides then state the two comparable numbers: `ms`, in milliseconds on both
sides, and `work_ratio`. `gflops` and `mfu` join the same way. Two shapes join
when they agree on every token they both state, so a bound that also names the
layer count still meets a measured row that does not.

`tools/nanochat attain --bench FILE --roofline FILE` performs the join. It is
the only place the two reports meet, and section 10 defines the record it
writes.

The phase sum is an attribution, not a new term. Each counter row carries one
phase, so the four sums add to `step_seconds`. A row that runs in both passes
becomes two rows of equal traffic. The total does not move, because a row with
no counted arithmetic splits linearly through the `max` of the estimator. The
quantization cast splits by operand role instead. The forward pass casts the
activation, and the backward pass casts the output gradient.

#### 7.4.1 The weighted peak

One peak cannot divide a mixed-precision step. At depth 24 the model rows hold
fp8 matrices, bf16 attention, and bf16 gates. A single fp8 denominator reads
low, and a single bf16 denominator reads above 1.0 and clamps. The model
reports the harmonic mean of the row peaks, weighted by the row arithmetic:

```text
weighted_peak = sum(flops_i) / sum(flops_i / peak_i)
```

At the depth-24 fp8 shape it is 1,827 TFLOP/s per device. A step that runs every
model row at its own peak reads 1.0 against it. So `model_mfu` and a measured
`mfu` share one denominator, and one fraction compares them.

#### 7.4.2 The two optimizer rows

The optimizer is two rows. `optimizer` is the state pass: fp32, sixteen bytes
per parameter, memory bound. `muon_orthogonalisation` is the Newton-Schulz work
of `EstimateMuonFlopsPerStep` at the compute type, and it is compute bound. The
plan's `muon_ns_steps` selects it, and zero keeps the report memory only.

Both rows are **replicated**. Every rank holds the whole parameter set, so the
optimizer traffic does not divide by the world size. The token-proportional rows
do divide, because their counts are world-wide. At the depth-24 shape on eight
cards the difference is 6.6 ms of optimizer state per step, not 0.8 ms.

The Muon arithmetic is 2.6e13 FLOP per step at depth 24. On eight H100 cards at
bf16 it is 26.4 ms of the step bound. It is reported beside the model count and
never added to it, because `mfu.h` keeps the two numerators apart.

#### 7.4.3 At the depth-24 shape

```
tools/nanochat roofline --devices 8 --device h100 --precision fp8 --layers 24 \
  --heads 12 --kv-heads 12 --hidden 1536 --seq 2048 --batch 16 --grad-accum 4 \
  --tokens 5.84e9 --link-gbps 600 --muon-ns-steps 5
```

| Number | At the bound |
|---|---:|
| The forward phase | 217.6 ms |
| The backward phase | 340.1 ms |
| The optimizer phase | 33.0 ms |
| The gradient sync | 16.1 ms |
| The step bound | 606.8 ms |
| The run bound over 5,570 steps | 3,380 s (56.3 min) |
| Tokens per second | 1,727,927 |
| Model FLOP utilization | 56.4% |
| Muon FLOP utilization | 4.3% |
| The weighted peak | 1,827 TFLOP/s |

The forward and the backward phase carry 92% of the step. A measured `fwd_ms`
plus `bwd_ms` above 558 ms is the first thing to explain. The per-row `mfu`
column names the family that is short.

#### 7.4.4 The JSON

`--json` writes `nanochat.roofline.v3`. It carries the identity of the run
(`device`, `precision`, `shape`), the phase fields, the two utilization numbers,
the weighted peak, and one object per row. A row states `name`, `family`,
`phase`, `precision`, `shape`, the counter fields, `bound_seconds`, `ms`,
`limit`, `gflops`, `work_ratio`, and `mfu`.

The version moved to 3 with the identity keys, the millisecond unit, and the
predicted work ratio. A `v2` document is refused by `attain` with the version it
found, because two reports from different versions describe different work.

The chain of [post-training.md](post-training.md) does not pass
`--muon-ns-steps`, so gate G3 compares its prediction with the model arithmetic
only, as section 7.3 records.

## 8. The work-ratio check

A row states two counts. `flops` is the arithmetic the operation must do, and
`issued_flops` is the arithmetic it hands the device. Their ratio is the work
ratio.

The counter table counts necessary work, so the model sets the two equal and
the predicted ratio reads 1.0. That is not a placeholder: it is the claim that
the model knows of no redundancy in that family. A measured ratio above 1.0 is
then the kernel's redundancy against a model that assumes none, and one field
compares the two.

- The benchmark's `work_ratio` is the issued work over the necessary work.
- The model's `work_ratio` is `issued_flops / flops`, and 0 when the row counts
  no arithmetic.

`docs/performance.md` section 3.1 gives the precedent. The earlier attention
tile recomputed the query-key product once per owned output dimension, so the
issued work grew with the square of the head width. A measured ratio near 2.0
at `d8_s512` shows that fault with no device in the loop, and the predicted 1.0
beside it shows what the operation should cost.

For the fp8 path the ratio covers one more case: the passes over an operand.
Four passes over an activation to measure, scale, cast, and copy it is three
passes more than the minimum. A cast row counts no arithmetic, so its ratio
reads 0 and the surplus shows in its byte count against the one pass the
operation needs.

## 9. The reference points

A bound alone does not say whether a kernel is good. Compare the measured rate
with the bound for the same family.

| Reference | Measured | Bound | Fraction |
|---|---:|---:|---:|
| The `lm_head` GEMM, `M=16384 N=32768 K=768`, fp32, T4, in PyTorch | 92.9 ms | 8.1 TFLOP/s | 1.09 |
| The same GEMM in nanochat.cpp, before the call fix | 229.1 ms | 8.1 TFLOP/s | 0.44 |
| The full d12 forward, `B=16 T=1024`, fp32, T4 | 679 ms | 8.1 TFLOP/s | — |
| The attention forward, `d8_s512` window 128, fp32, GTX 1080 Ti | 1.087 ms | 11.34 TFLOP/s | — |
| The depth-24 run, eight H100 cards, fp8 | 99 min | about 57 min | 0.57 |

Two lessons come from the table.

1. **A fraction above 1.0 means the table peak is wrong.** The first row is
   8.8 TFLOP/s measured against an 8.1 TFLOP/s table value. The table rate is
   likely a base-clock value. Fix the table, and do not absorb the fault into a
   factor.
2. **The fraction is a diagnostic, not an input.** The 0.44 row is a real
   defect that the fix in `backends/cuda/gemm.cu` removed. The model points at
   the family; the measurement confirms it.

The d24 fraction of 0.57 is the target to beat. Each of the four gap items in
section 7.2 is a separate investigation.

## 10. The attainment record

The record is generated, not transcribed. `tools/nanochat attain` joins a bound
and a measurement and prints the row:

```
tools/nanochat attain --bench bench.json --roofline roof.json --markdown
```

It reads a `nanochat.roofline.v3` document and a `nanochat.bench.v3` document,
joins their rows on the four identity keys of section 7.4, and prints the
fraction of the bound the device reached. `--json` writes
`nanochat.attainment.v1` for a reader that wants the numbers.

| Column | Meaning |
|---|---|
| Bound (ms) | The row's roofline bound |
| Measured (ms) | The benchmark row's time |
| Fraction | The bound over the measurement |
| Issue/need | The measured work ratio, beside the predicted 1.0 |
| Limit | The limit the bound names: compute, memory, or launch |
| Validated on | The device the measurement ran on |
| Gap cause | The note the join writes: an unjoined row, a fraction above 1.0, or a bound tested on another card |

Two rules come out of the join and are enforced by it:

1. **A fraction above 1.0 is a finding.** The fraction is reported unclamped. A
   value above 1.0 means the declared peak rate is too low or the measurement
   does not count the work the bound counts. Section 9 asks for the first, and
   the note names both.
2. **A bound is validated on one card.** A bound for one device says nothing
   about another, and the model cannot time a card it cannot run on. Each row
   therefore names the device that tested it, and the join states plainly when
   the bound and the measurement name different cards.

The record for the depth-24 shape:

| Date | Revision | Device | Build | Precision | Configuration | Bound | Measured | Fraction | Validated on | Gap cause |
|---|---|---|---|---|---|---|---|---|---|---|
| — | reference `a825e63` | 8 x H100 | fp8 | fp8 | d24, batch 16, grad-accum 4, 5.84e9 tokens | 57 min | 99 min | 0.57 | reference PyTorch run | The reference run, not this tree (docs/node-h100.md) |
| — | this tree | 8 x H100 | fp8 | fp8 | d24, batch 16, grad-accum 4, 5.84e9 tokens | 56 min | pending | — | pending | The bound includes the row kernels and the two optimizer rows, from `tools/nanochat roofline --muon-ns-steps 5` |

The record is the audit trail. A bound without a measurement is a limit, and
the row says so.

`docs/baselines.json` is a different artifact. It holds the frozen baseline of
the shipped path at a named revision, and each entry names the command that
measured it and the device that validated it. The record above is the comparison
of a bound with a measurement at one revision, and it is generated.

## 15. Risks and non-goals

- **The bound is an upper limit, not a prediction.** A run below the bound is
  normal. Section 7.2 shows how to split the gap.
- **A declared peak may be wrong.** Section 9 records one such case. Check the
  declaration before you judge a kernel, and remember that the declaration is
  now the only table, so a wrong number reaches the MFU line, the benchmark
  share, and the bound together.
- **Measurement cannot find a missing counter term.** If the counter table
  omits the cast traffic, the bound is wrong by 13 minutes. Review the counter
  table against `docs/kernels.md`.
- **The precision assignment can drift from the code.** Keep the assignment in
  one function, and unit-test it against the layer set in
  [fp8-training.md](fp8-training.md).
- **The bandwidth peak is hard to reach.** The memory term is a bound, like
  the compute term.
- **The phase split is an attribution.** The row kernels split evenly between
  the two passes. The counter table does not count the extra pass a weight
  gradient needs, so that term is understated in both phases.
- **The optimizer rows are replicated.** A sharded optimizer would divide them
  by the world size. The tree's optimizer holds the whole parameter set on every
  rank, so the rows do not divide today.
- **The launch cost is a device property.** Record it in the table. Do not set
  it per shape.
- **Not a goal:** a fitted correction, a cycle-accurate model, a cache model,
  and a full memory simulation.

## 16. Open questions

1. The counter struct lives beside `NumMatmulParams` in
   `src/performance_model.cc`, next to the estimator that reads it. The
   declaration is in `include/nanochat/mfu.h`.
2. The estimator lives in the C library, in `src/performance_model.cc`.
3. The report goes to the training log, and `nanochat_cli roofline` also writes
   the `nanochat.roofline.v3` JSON.
4. The launch cost lives in `DeviceProfile::launch_us`.
5. The C++ fp8 path stores the weight transposed. The estimator models the
   reference copies behind `ModelPlan::transposed_weights`.
6. The Muon iteration count lives in `ModelPlan::muon_ns_steps`, because the
   estimator has no optimizer configuration of its own.
